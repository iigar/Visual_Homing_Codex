# Програмна перевірка Visual Homing — 2026-09-21

## Межа перевірки

Перевіряється локальна програмна частина у WSL/GCC, з усіма сімома
`VISUAL_HOMING_*` camera/output build options у стані `OFF`.
Це перевірка конкретних програмних контрактів, не оцінка точності розпізнавання
на реальному повторному проході й не hardware/flight acceptance.

Попередні завершені CMake, shell parser, endpoint/dwell і readiness refactors
зафіксовано комітом `5793361`. Перед новою зміною Debug CTest пройшов `50/50`.

## Виправлення конфігурації

| Випадок | Перевірена проблема | Нова поведінка |
|---|---|---|
| `" -1"`, табуляція/перенесення рядка перед мінусом | `stoull` приймав від'ємне число після пропуску першого пробільного символу | Мінус перевіряється після початкових пробільних символів; значення відхиляється |
| `4294967297` для MAX_KEYFRAMES/DESCRIPTOR_DIMENSIONS | Перетворення з `size_t` у `uint32_t` давало `1` на 64-бітній збірці | Перевірка межі `uint32_t` до приведення, незалежно від розміру `size_t` |
| `18446744073710` мс для MIN/MAX_INTERVAL_MS | Множення на мільйон переповнювалося до `448384` нс | Перевірка `UINT64_MAX / 1000000` до множення |
| `NaN`/нескінченності | CLI приймав не скінченні значення; endpoint/rollback validation пропускала NaN | Спільний double CLI parser відхиляє не скінченні числа; три runtime-поля мають також незалежний захист для викликів бібліотеки |

Збережено допустимий синтаксис: початкові пробіли, знак `+`, науковий запис
скінченних чисел. Діапазони endpoint лишаються `[0, 1]` із `start < end`;
rollback лишається невід'ємним. Нових порогів якості або readiness не додано.
Інші прямі виклики `std::sto*` в CLI не входили до цього обмеженого виправлення.

## Як перевіряється

- `cli_numeric_arguments` запускає справжній executable через CMake, очищає
  успадковані `VISUAL_HOMING_*` env settings і виконує 60 випадків. До виправлення
  35/60 не відповідали очікуваній валідації. Включені обидва uint32-поля,
  обидва інтервали, граничні допустимі числа, різні пробільні символи,
  NaN/Infinity та позитивні контрольні приклади.
- Допустимі аргументи мають дійти до читання навмисно відсутнього route-файлу;
  недопустимі — відхилятися з правильною причиною раніше. Це контроль межі
  валідації, а не успішний запуск live matching. Камера не ініціалізується.
- `live_route_config` викликає production API напряму. Перевіряє NaN,
  нескінченності, негативні значення, точні межі, найближчі числа поза діапазоном
  та порядок endpoint-порогів. Це не дозволяє CLI-перевірці приховати дефект API.
- Обидва сценарії включені у CTest. CMake CLI test не додає Python/Bash
  залежностей до core-тестів на Windows.

Повторення повного локального набору:

```sh
bash scripts/test-software.sh
```

Окремий запуск нових тестів після збірки:

```sh
ctest --test-dir core/build-software/Debug --output-on-failure \
  -R '^(live_route_config|cli_numeric_arguments)$'
```

## Що ще потрібно для оцінки системи

| Питання | Поточне свідчення | Чого бракує |
|---|---|---|
| Чи виконуються перевірені програмні правила? | Unit/CLI/replay tests, включно з негативними сценаріями | Це не повний перебір станів і не виміряне покриття всіх гілок |
| Чи впізнається маршрут на незалежному проході? | Є PGM loader і matcher; у перевірених `artifacts/`, `keyframes/`, `config/` знайдено 37 окремих PGM | Повний незалежний запис повторного проходу та еталонна розмітка |
| Чи правильно взаємодіє весь live цикл у часі? | Окремі тести компонентів; replay має власний цикл, scripted telemetry та relaxed age limits | Наскрізний offline-сценарій актуальної live-логіки з контрольованими часовими мітками і відмовами |
| Чи вкладається matcher у бюджет затримки/пам'яті? | Історичний Pi benchmark стосувався native capture/publication | Окремий відтворюваний matcher benchmark із p50/p95/p99 та RSS |
| Чи працює актуальна версія на Pi? | Історична Pi validation належить попередній версії | Повторна перевірка актуального коміту на цільовому обладнанні |

Наявність повних записів на Pi або в інших каталогах тут не перевірялася.
Для наступного аналізу потрібні: маршрут першого проходу, кадри другого проходу,
їхні timestamps, camera profile/налаштування та незалежні позначки фактичних
ділянок маршруту. Сценарії поза маршрутом і зі схожими місцями потрібні для
перевірки хибного розпізнавання. Наявні пороги слід зіставити з вимогами;
нові критерії прийнятності не можна виводити лише з відповіді самого matcher.
