# Швидше порівняння масштабованих кадрів — 2026-09-25

Цей крок продовжує `1345ab9`: попередній early exit прискорив exact self-match,
але не дав помітного виграшу на 13 stop-кадрах із ненульовою похибкою.
Тому спочатку виміряно частку часу scale kernel, потім прибрано повторний
розрахунок координат у його внутрішньому циклі.

## Підстава для оптимізації

У тимчасовій копії початкового matcher додано `steady_clock`-таймери навколо
`match` та `scaled_normalized_mean_absolute_difference`. Ця діагностична збірка
показала медіанну частку kernel **80.36%** сумарного часу `match`.
За знімками частка становить приблизно 72–81%, 48 або 72 kernel-виклики на query
(два або три сусіди × 24 масштаби). Три процеси на кожен із 13 hash-verified PGM,
чотири виклики matcher у процесі, включно з прогрівальним.

Це приблизна атрибуція з витратами таймерів. Остаточні виміри швидкодії виконано
окремими звичайними Release executable без цієї інструментації.
Артефакти: `profile.py`, `instrumented-matcher.cpp`, `profile-results.json`,
`profile.log` у `artifacts/scale-kernel-20260925/`.

Повторення такої самої інструментації після оптимізації дало **21.94%** часу
в kernel; кількість kernel-викликів та результат залишилися тими самими.
Отже, для наступного кроку варто окремо виміряти решту `match`: coarse scan
і формування кандидатів. Частка поза kernel сама по собі ще не визначає,
який саме з цих компонентів домінує. After-profile artifacts мають префікс `after-`.

## Що змінилося

Єдина production-функція зі зміненим тілом —
`scaled_normalized_mean_absolute_difference` у `core/src/gray8_route_matcher.cpp`.

- X-координати обчислюються один раз на блок до 128 стовпців і використовуються
  для всіх рядків. Y-координата обчислюється один раз на рядок кожного непорожнього
  блока. Немає повторення цих floating-point операцій для кожного пікселя.
- Два локальні масиви по 128 `int` займають сумарно 1024 bytes на перевіреній
  x86_64-збірці. Розмір scratch storage не залежить від розміру кадру; heap-виділень,
  кешу, нового стану matcher або shared mutable state немає.
- Вирази координат із діленням та `std::lround` збережено дослівно. Reciprocal,
  epsilon або інтерполяція не вводяться. Набір пікселів перекриття той самий.
- Порядок обходу змінений на блоки, але накопичення — цілочисельні `uint64_t`
  та `size_t`: підсумкова сума і кількість однакові. Формула нормалізації не змінена.
- Список масштабів, tie policy, early exit, confidence, progress/window policy
  та caller validation залишаються попередніми.

Спільний kernel викликають matcher refinement і `scaled_reference_distance`
для visual-scale diagnostics. Файли camera runtime та output не редагувалися;
жодної апаратної перевірки чи підключення до борту не виконувалося.

## Перевірка еквівалентності

Новий `gray8_scale_distance_test` містить заморожену початкову scalar-формулу
з `1345ab9`, незалежну від блочного обходу production-коду. Тест спочатку пройшов
на архівованому baseline, потім на новій реалізації:

- **11019 побітово однакових double-результатів**, без tolerance;
- усі 24 production scales та сусідні representable значення біля 0.3, 0.5, 1, 1.5;
- випадкові детерміновані пікселі, крайня різниця 0/255 та однакові візерунки;
- парні/непарні розміри, 1-піксельні сторони, межі блоків 127/128/129,
  255/256/257, кадри 160×100, 640×480 і 1280×720;
- порожні розміри, відсутність перекриття, нульові/від'ємні/нескінченні/NaN scales.

Debug і Release **56/56 CTest**, readiness Python **15/15**, benchmark helpers
**5/5**. У Release assertions нового тесту активні (`-UNDEBUG` після `-DNDEBUG`).
Окремий запуск цього ж тесту з AddressSanitizer + UBSan успішний, exit 0,
без повідомлень про помилки. `BUILD_TESTING=OFF` збирається і реєструє 0 тестів.
Усі сім camera/output flags у трьох конфігураціях OFF.

## Виміри на записах

Усі **44 сценарії** дали однакові результати: шість маршрутів у трьох режимах
та 13 PGM у двох режимах. На кожен варіант виконано **69741 вимірюване
self-зіставлення** і **234 PGM-зіставлення**, без урахування прогріву.

На 13 PGM із ненульовою похибкою та ввімкненим refinement медіана часу
зменшилася **14.197 → 3.474 ms**. Медіана парних відношень після/до — `0.245`:
приблизно **4.1 раза швидше**, або на **75.5% менше часу** в цьому наборі.
Для окремих знімків прискорення становить 3.21–4.19 раза.

лише `match`, без завантаження файла та створення matcher. Ідентифікатор знімка

Контрольні режими залишилися практично незмінними: медіана парних відношень
після/до `self-global=1.004`, `self-window30=1.000`, `self-window30-scale=1.000`,
`pgm=0.998`. У self-scale exact matches kernel уже пропускається завдяки попередній
оптимізації. Порівняння проведено на WSL2 x86_64 / Intel Core i5-10300H;
це не гарантія real-time latency чи такий самий коефіцієнт на Pi.

В обох варіантах використано той самий `gray8_matcher_benchmark.cpp` та GCC 13.3
`-std=c++20 -O3 -DNDEBUG -Wall -Wextra -Wpedantic -pthread`; baseline source/header
узято з ізольованого `git archive 1345ab9 core`, після — із поточного checkout.
Три свіжі процеси кожного варіанта на сценарій, порядок before/after чергується;
один прогрівальний і три вимірювані проходи в кожному процесі. Час охоплює лише
`match`, а рівність перевіряється за всіма полями match і top candidates.

```sh
python3 scripts/compare-scale-refinement.py \
  --before artifacts/scale-kernel-20260925/before-benchmark \
  --after artifacts/scale-kernel-20260925/after-benchmark \
  --inventory artifacts/board-inventory-20260922 \
  --output-dir artifacts/scale-kernel-20260925/comparison-repeat
bash scripts/test-software.sh artifacts/config-validation-20260921/clean-build
```

Сирі JSONL та `comparison/summary.json` містять виміри, executable/source/input
SHA-256 і явну прив'язку знімків до маршрутів за журналами. Локальні build/profile/
test artifacts збережено під ignored `artifacts/scale-kernel-20260925/`.
Зведені числа збережено у `timing-summary.json` та `timing-summary.txt`.
Виміри стосуються WSL-комп'ютера, не Pi або live pipeline; шість власних записів
маршрутів і 13 окремих PGM не замінюють розмічений повний повторний прохід.

## Область впливу

GitNexus impact перед змінами — неповний `UNKNOWN`. Direct source search
підтвердив два production callers: refinement helper і visual-scale wrapper.
Після оновлення індексу `detect_changes` показав `critical`/211 процесів, але
прив'язав їх до kernel з порожнім symbol ID, включно зі сторонніми JSX-процесами.
`context` також показує сторонні доступи до navigator/publisher замість надійного
call graph. Це обмеження інструмента збережено, його рейтинг не є acceptance.
Graphify і GitNexus CLI індекси оновлено; перевірка спирається на прямий diff,
scalar oracle та реальні before/after результати.

Фінальна staged-перевірка охопила 6 очікуваних файлів і показала 166 процесів:
162 приписано лише empty-ID kernel, ще 4 сторонні JSX-процеси — kernel і file node.
Порівняння всієї гілки з `main` охопило 41 файл та 211 процесів: 209 прив'язано
лише до порожнього README symbol, решта два parser flows стосуються попереднього
numeric configuration fix. Ці відомі обмеження не змінюють фактичний staged diff.
Збережено `gitnexus-{unstaged,staged,compare}-summary.json` в артефактах.
